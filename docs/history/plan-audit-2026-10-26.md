# Plan implementation audit

Checked on 2026-10-26 against the current source and focused automated tests. The detailed plans describe the intended product; this page records what has actually been verified.

| Plan | Implemented in source | Automated verification | Remaining acceptance work |
|---|---|---|---|
| [Core product](../../plan.md) | Pipeline, editor, AI direction, Shorts and Social surfaces exist. | The core plan's older measurements are historical and were not rerun in this audit. | Its listed M2, cold-open, talking-head polish, taste, and product gates remain open. |
| [Shorts](PLAN-SHORTS.MD) | Detector and prompts (`vt/shorts`), sentence snapping, child project slicing, API routes, and Studio page with direct video upload, source video review, swipe/arrow navigation, caption and speaker options, and batch export. | [Live QA](../qa/shorts-ui-2026-10-26.md): 7 backend tests, browser control smoke test, accepted video upload form, and one real candidate-to-Short render with A-roll in 4/4 scenes. | Run candidate detection and batch rendering on three long videos; get human agreement on at least 3 of the top 5 picks; inspect sentence boundaries and face framing. The Shorts page links to each child's Result page for Social publishing rather than posting directly. |
| [Social](PLAN-SOCIAL.MD) | SQLite queue and worker (`vt/social/core.py`), Meta/Instagram/YouTube/TikTok upload branches, account and group API, Result dispatch, Social hub, logs and retry. | `tests/test_social_flow.py` covers mock dispatch, isolation of failed tasks, retry, path rejection and an Instagram upload with mocked HTTP. | Connect real accounts and confirm one live post and stored permalink per platform. Other live platform flows and rate limits lack live verification. The plan names separate adapter modules; current implementation keeps them in `core.py`. The plan's account connection flow is token entry/Meta token exchange, not a complete OAuth login UI for every platform. |
| [Director modules](PLAN-DIRECTOR-MODULES.MD) | Decided 2026-10-26 (owner). Every capability is a module with declared inputs and outputs; the director (rules, one-shot plan, agent, or an external assistant over MCP) calls any module at any point. About 142 modules, every one of the 121 source files mapped. Includes the plan review (the plan is shown, editable, before anything expensive runs) and the live director log behind a button. | Inventory taken from the code (121 files, 31 MCP tools, the project folder's artifact files). Nothing built: the registry, workspace, executor and call log do not exist yet. | Phase 0 (contract spike, three modules) then phase 1 (the 12 pipeline stages as modules with byte-identical output). |
| [Audio-first direction](PLAN-AUDIO-FIRST-DIRECTOR.MD) | Decided 2026-10-26 (owner). The audio is cut first; a director marks impact points and picks each slot's medium; generated clips are small silent inserts. | Research gathered (sources and caveats in the plan); the parts it builds on exist: sentence-level speech, cleaning and cutting, prosody, saliency, sound events, the media menu. | Nothing of the new flow is built: impact map, direction schema and eval set, cut plan, medium budget, measured word times for script speech, generated-clip wiring. First step is the 20-clip direction set with human edits. |
| [ComfyUI video](PLAN-COMFYUI-VIDEO.MD) | `vt/comfy/` (client, workflows, job), `vt/server/comfy_routes.py`, Settings card, media-bin "Generate motion clip" with a framing window, Ollama GPU release; two verified engines (Wan 2.2, LTX-2.3). | `tests/test_comfy.py` (10, fake server), `e2e/comfy.mjs` (8, real server); real clips through the Studio API on the V100: LTX 126 s warm, Wan 55-67 s warm, looked at. Server rebuilt for the V100 ([runbook](../ops/comfyui-server.md)). | a person can place a generated clip in the timeline and it renders with captions, but nothing decides where footage belongs or what it shows; Shorts child projects do not offer it yet; frame interpolation. The first test used an unrelated stock picture: choosing the moments and writing the prompt from the speaker's words is not built. |

The project root keeps `plan.md` because code and historical documents refer to it. The detailed plans live here. Source, user projects, settings, models, generated renders, QA outputs, and sample media retain their existing paths because scripts and tests refer to some of them directly.
